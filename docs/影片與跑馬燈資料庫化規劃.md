# 四維商圈行程表：影片與跑馬燈資料庫化規劃

- 文件狀態：規劃版，可作為後續實作依據
- 建立日期：2026-07-12
- 適用專案：`niceshow` / `https://siwei.pages.dev/`
- 建議技術：Cloudflare Pages + Supabase Auth + Supabase Database + Supabase Storage

## 1. 結論摘要

本專案不需要再增加另一套資料庫。現有網站已經使用 Supabase 讀取行程資料，後台也已安裝 `@supabase/supabase-js` 並具備圖片上傳雛形，因此最穩定、維護成本最低的做法是沿用同一個 Supabase 專案，把媒體管理補完整。

資料應分成兩種保存方式：

1. 影片、圖片等大型檔案放在 Supabase Storage，不直接塞進資料庫欄位。
2. 標題、來源、排序、上架狀態、發布時間、跑馬燈位置、連結及檔案路徑放在 Supabase Database。

網站之後只從 Supabase 讀取「已發布」資料；管理者則從後台登入後完成上傳、預覽、排序、上架、下架。這樣新增影片或更換跑馬燈內容時，不必再修改 `index.html`、下載 `data.json`、提交 GitHub 或等待重新部署。

建議保留兩種影片來源：

- 自行上傳：MP4 檔案上傳至 Supabase Storage，由網站原生播放器播放。
- TikTok 連結：只在資料庫保存 TikTok 正式網址與影片 ID，由網站動態建立 TikTok 嵌入內容，不重新下載或複製 TikTok 影片。

第一階段建議使用 Supabase Storage 播放短影片。若未來直接上傳的影片成為主要內容，且出現大量觀看、行動網路卡頓或需要自動畫質切換，再把影片提供者換成 Cloudflare Stream。資料表會預留 `provider` 欄位，屆時不必重新設計後台與頁面。

## 2. 現況盤點

### 2.1 現有資料來源

| 區域 | 現在的來源 | 現在的更新方式 | 主要問題 |
|---|---|---|---|
| 行程表 | Supabase `foodcarcalss` | 由現有資料流程寫入，前台直接讀取 | 已可使用，這次不需要搬動 |
| 影片觀賞區 | `index.html`、`v2.html` 內的 TikTok HTML | 手動修改 HTML、提交、部署 | 每次改片都要改程式；兩份 HTML 可能不同步 |
| 跑馬燈主資料 | `data.json` | 後台匯出 JSON，再手動取代檔案 | 後台的修改不是直接存入正式資料 |
| 跑馬燈瀏覽器快取 | `localStorage.foodTruckData` | 瀏覽器自行保存 | 容易讓部分使用者看到舊資料 |
| 跑馬燈備用資料 | `script.js` 內硬編碼陣列 | 修改 JavaScript | 與 `data.json` 重複，可能出現第三種版本 |
| 餐車自助登錄 | Google Apps Script / Google Sheets / Cloudinary | `sheets-marquee.js`、`upload.js` | 與 Supabase 媒體管理分離，且目前主頁未設定 Apps Script URL |
| 圖片檔案 | Cloudinary、Postimg、Supabase Storage 混用 | 多個入口 | 刪除、搬移、權限、失效連結難統一管理 |
| 後台登入 | 前端寫死密碼 + `localStorage` | 瀏覽器本機判斷 | 任何人都可繞過，不可用來保護資料庫寫入 |

### 2.2 已確認的程式現況

- `sheets-booking.js` 已從 Supabase 資料表 `foodcarcalss` 讀取行程。
- `index.html` 與 `v2.html` 的影片是硬編碼 TikTok blockquote。
- `index.html` 與 `v2.html` 目前至少有一支 TikTok ID 不一致，代表雙檔維護已經開始產生版本漂移。
- `admin/src/pages/VideoManagement.jsx` 只修改 React 記憶體狀態，儲存後仍提示要手動更新 `index.html`。
- `admin/src/pages/ImageManagement.jsx` 可上傳圖片至 Storage，但圖片清單最後仍是匯出 JSON，不會直接寫入 Database。
- `admin/src/pages/Login.jsx` 的密碼直接存在前端程式，`admin/src/App.jsx` 只用 `localStorage` 判斷登入。
- `admin/src/config/supabase.js` 使用的 bucket 名稱為 `niceshow`，舊文件另寫 `food-truck-images`，命名需要統一。
- 網站目前用 `_headers` 對所有路徑設定 `no-store`，能降低舊版殘留，但也讓可長期快取的靜態資源無法有效快取。

### 2.3 目前最需要解決的維護問題

1. 同一內容存在 HTML、JSON、JavaScript、localStorage、Google Sheets 等多個版本。
2. 後台看似可以編輯，但沒有真正持久化到正式資料庫。
3. 新增影片仍需要懂 HTML、Git、部署與快取版本。
4. 管理權限只存在前端，正式接上資料庫寫入後會有安全風險。
5. 更換同網址檔案時，CDN 或內嵌瀏覽器可能繼續取得舊檔。
6. 圖片與影片沒有統一的發布狀態、排程、排序、刪除與異常回復流程。

## 3. 專案目標與邊界

### 3.1 本次目標

- 後台可上傳 MP4 影片並看到真實上傳進度。
- 後台可貼上 TikTok 長網址或短網址，自動取得正式網址與影片 ID。
- 後台可管理跑馬燈圖片，也可選擇放入短版靜音影片。
- 所有媒體內容可設定草稿、發布、封存、排序、開始時間與結束時間。
- 公開網站只顯示已發布且在有效時間內的內容。
- 更新內容不再需要修改 HTML、JSON 或重新部署網站。
- 手機版保留目前的左右滑動、左右按鈕與圓點導覽。
- 保留目前「排班餐車才出現在跑馬燈」的能力。
- 解決舊內容快取與同網址覆蓋造成的版本不一致。
- 正式後台改用 Supabase Auth 和 RLS 權限。

### 3.2 暫不納入第一階段

- 不重做整個行程表資料模型。
- 不立即移除 `foodcarcalss` 或變更現有行程資料流程。
- 不在瀏覽器內進行完整影片轉檔。
- 不建立公開會員系統；只建立管理員帳號。
- 不在第一階段導入複雜即時協作或多人審核流程。
- 不把 TikTok 影片下載後重新上傳，以免增加版權、空間與流量負擔。

## 4. 建議架構

```text
管理者
  |
  v
Cloudflare Pages 後台（React/Vite）
  |-- Supabase Auth：管理員登入
  |-- Supabase Database：媒體資料、排序、上下架、連結
  |-- Supabase Storage：圖片、MP4、封面圖
  `-- Supabase Edge Function：解析 TikTok 短網址（建議）

公開訪客
  |
  v
https://siwei.pages.dev/
  |-- 讀取 Supabase 已發布媒體資料
  |-- Storage 圖片/影片：原生 HTML 播放
  `-- TikTok：動態嵌入官方播放器
```

### 4.1 各服務責任

| 元件 | 責任 | 不應負責 |
|---|---|---|
| Cloudflare Pages 公開網站 | 顯示行程、影片、跑馬燈與互動控制 | 保存影片檔案、判斷管理權限 |
| Cloudflare Pages 後台 | 登入、上傳、編輯、排序、預覽、發布 | 保存 service role key |
| Supabase Auth | 驗證管理員身分、簽發登入權杖 | 用前端硬編碼密碼替代 |
| Supabase Database | 保存媒體中繼資料與發布規則 | 保存 MP4 binary 或 base64 |
| Supabase Storage | 保存圖片、影片、封面檔 | 保存標題、排序、上下架狀態 |
| Edge Function | 安全解析 TikTok 短網址、限制允許網域 | 將 Supabase service role key 傳給瀏覽器 |

### 4.2 為何先沿用 Supabase

- 現有公開網站已連接同一個 Supabase 專案。
- 現有後台已安裝 Supabase SDK 並有上傳元件，可在原結構上改造。
- Database、Auth、Storage、RLS 可以在同一個權限模型內完成。
- 對目前少量短影片和跑馬燈內容，維護一套服務比同時使用 D1、R2、Cloudinary、Google Sheets 更容易。

Supabase Storage 可以直接保存與提供圖片、影片，但它不會自動把一支影片轉成多種畫質。若未來需要自動轉碼、HLS/DASH、自動畫質或更完整的影片分析，則應改用 Cloudflare Stream；Database 仍只需要更換 `provider` 和 `provider_asset_id`，頁面與後台流程可繼續沿用。

## 5. 資料模型

### 5.1 核心資料表

建議第一階段建立四張表：

| 資料表 | 用途 |
|---|---|
| `admin_users` | 允許管理網站內容的 Supabase 使用者 |
| `site_media` | 跑馬燈與影片區的主要媒體資料 |
| `media_links` | 一筆跑馬燈內容可擁有多個按鈕連結 |
| `media_change_log` | 記錄新增、修改、發布、封存與刪除行為 |

### 5.2 `site_media` 欄位規格

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---:|---|
| `id` | uuid | 是 | 主鍵，建立時自動產生 |
| `placement` | text | 是 | `marquee` 或 `video_gallery` |
| `media_kind` | text | 是 | `image` 或 `video` |
| `provider` | text | 是 | `supabase_storage`、`tiktok`、`cloudflare_stream`、`external` |
| `title` | text | 是 | 後台與前台顯示標題 |
| `description` | text | 否 | 影片說明或備註 |
| `alt_text` | text | 否 | 圖片替代文字與無障礙用途 |
| `storage_bucket` | text | 視來源 | 預設 `site-media` |
| `storage_path` | text | 視來源 | Storage 物件路徑，不保存完整 Supabase URL |
| `external_url` | text | 視來源 | TikTok 或舊外部圖片網址 |
| `external_id` | text | 視來源 | TikTok video ID |
| `provider_asset_id` | text | 視來源 | 未來 Cloudflare Stream UID |
| `poster_path` | text | 否 | 影片封面圖的 Storage 路徑 |
| `mime_type` | text | 否 | 例如 `video/mp4`、`image/webp` |
| `file_size_bytes` | bigint | 否 | 檔案大小，用於管理與清理 |
| `width` / `height` | integer | 否 | 媒體尺寸 |
| `duration_seconds` | numeric | 否 | 影片長度 |
| `sort_order` | integer | 是 | 同一區域內的順序 |
| `status` | text | 是 | `draft`、`published`、`archived` |
| `publish_start` | timestamptz | 否 | 預約上架時間 |
| `publish_end` | timestamptz | 否 | 預約下架時間 |
| `display_rule` | text | 是 | `always` 或 `when_scheduled` |
| `vendor_match_names` | text[] | 否 | 餐車名稱與別名，用於比對排班資料 |
| `created_by` / `updated_by` | uuid | 是 | 對應 Supabase Auth 使用者 |
| `created_at` / `updated_at` | timestamptz | 是 | 稽核時間 |

### 5.3 建議 SQL 骨架

以下是規格骨架。正式執行前應先在 Supabase 測試環境套用並跑 RLS 測試，再套用正式環境。

```sql
create extension if not exists pgcrypto;

create table public.admin_users (
  user_id uuid primary key references auth.users(id) on delete cascade,
  role text not null default 'editor'
    check (role in ('owner', 'editor')),
  created_at timestamptz not null default now()
);

create table public.site_media (
  id uuid primary key default gen_random_uuid(),
  placement text not null
    check (placement in ('marquee', 'video_gallery')),
  media_kind text not null
    check (media_kind in ('image', 'video')),
  provider text not null
    check (provider in ('supabase_storage', 'tiktok', 'cloudflare_stream', 'external')),
  title text not null,
  description text not null default '',
  alt_text text not null default '',
  storage_bucket text,
  storage_path text,
  external_url text,
  external_id text,
  provider_asset_id text,
  poster_path text,
  mime_type text,
  file_size_bytes bigint check (file_size_bytes is null or file_size_bytes >= 0),
  width integer check (width is null or width > 0),
  height integer check (height is null or height > 0),
  duration_seconds numeric(10, 2)
    check (duration_seconds is null or duration_seconds >= 0),
  sort_order integer not null default 0,
  status text not null default 'draft'
    check (status in ('draft', 'published', 'archived')),
  publish_start timestamptz,
  publish_end timestamptz,
  display_rule text not null default 'always'
    check (display_rule in ('always', 'when_scheduled')),
  vendor_match_names text[] not null default '{}',
  created_by uuid references auth.users(id) on delete set null,
  updated_by uuid references auth.users(id) on delete set null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint site_media_source_required check (
    (provider = 'supabase_storage' and storage_path is not null)
    or (provider = 'tiktok' and external_url is not null and external_id is not null)
    or (provider = 'cloudflare_stream' and provider_asset_id is not null)
    or (provider = 'external' and external_url is not null)
  ),
  constraint site_media_publish_window check (
    publish_end is null or publish_start is null or publish_end > publish_start
  )
);

create index site_media_public_list_idx
  on public.site_media (placement, status, sort_order);

create index site_media_publish_window_idx
  on public.site_media (publish_start, publish_end);

create table public.media_links (
  id uuid primary key default gen_random_uuid(),
  media_id uuid not null references public.site_media(id) on delete cascade,
  label text not null,
  url text not null,
  sort_order integer not null default 0,
  is_active boolean not null default true,
  created_at timestamptz not null default now()
);

create index media_links_media_idx
  on public.media_links (media_id, sort_order);

create table public.media_change_log (
  id bigint generated always as identity primary key,
  media_id uuid references public.site_media(id) on delete set null,
  action text not null,
  changed_by uuid references auth.users(id) on delete set null,
  before_data jsonb,
  after_data jsonb,
  created_at timestamptz not null default now()
);
```

### 5.4 為何不把所有欄位塞在一個 JSON

- 排序、發布時間與狀態需要能直接查詢和建立索引。
- RLS 需要依欄位判斷公開讀取條件。
- 多個連結獨立成 `media_links`，後台新增、刪除和排序比較穩定。
- 媒體提供者獨立成 `provider`，未來從 Storage 換到 Stream 時不必改整張表。

### 5.5 餐車名稱比對的過渡方案

現在的行程表只有 `vendor` 文字，沒有穩定的餐車 ID。為避免這次改動擴大，第一階段先使用：

- `display_rule = 'always'`：無論排班都顯示。
- `display_rule = 'when_scheduled'`：只有本期行程出現相符名稱才顯示。
- `vendor_match_names`：保存店名及常見別名，沿用目前的正規化比對邏輯。

第二階段若要徹底改善，可新增 `food_trucks` 主檔並讓 `foodcarcalss`、`site_media` 都引用同一個 `food_truck_id`。在這之前不建議直接修改現有行程表資料結構。

## 6. Storage 規格

### 6.1 Bucket

統一建立一個 public bucket：`site-media`。

public 代表知道檔案網址的人可以讀取，適合本來就要公開顯示的網站素材；上傳、更新、搬移與刪除仍必須由 RLS 限制為管理員。草稿媒體若有保密需求，才需要另外建立 private bucket 和簽名網址；目前網站內容不需要增加這項複雜度。

### 6.2 物件路徑

```text
marquee/images/{yyyy}/{mm}/{uuid}-{slug}.webp
marquee/videos/{yyyy}/{mm}/{uuid}-{slug}.mp4
gallery/videos/{yyyy}/{mm}/{uuid}-{slug}.mp4
posters/{yyyy}/{mm}/{uuid}-{slug}.webp
```

規則：

- 每次更換檔案都建立新 UUID 路徑。
- 不覆蓋舊物件，不使用固定的 `video.mp4` 或 `banner.jpg`。
- Database 只更新到新路徑，確認網站正常後再清理舊物件。
- 原始檔名只作顯示，不作唯一識別。

這項規則可以避免 CDN 已經快取同一網址時，部分使用者繼續看到舊影片或舊圖片。

### 6.3 第一階段上傳限制

| 項目 | 建議限制 | 原因 |
|---|---|---|
| 影片容器 | MP4 | iOS、Android、桌面瀏覽器相容性最好 |
| 影片編碼 | H.264 + AAC | 不做伺服器轉碼時最穩定 |
| 影片大小 | 預設 100 MB，可在設定調整 | 避免行動網路上傳與播放負擔過重 |
| 影片長度 | 建議 60 秒內，最多 90 秒 | 符合目前短影音用途 |
| 影片尺寸 | 直式 1080x1920 或 720x1280 | 對應目前手機輪播 |
| 跑馬燈影片 | 建議 8 秒內、靜音、循環 | 避免多支影片同時大量耗流量 |
| 圖片格式 | WebP、JPEG、PNG | 優先 WebP |
| 圖片大小 | 5 MB 以下 | 維持目前後台限制 |

實際可上傳上限仍受 Supabase 專案全域與 bucket 設定影響。bucket 應限制允許的 MIME type 和最大檔案大小。

### 6.4 大型影片上傳方式

影片不應繼續沿用現在圖片元件的一次性 `.upload()` 流程。Supabase 官方建議檔案超過 6 MB 或網路可能不穩時使用 TUS resumable upload，因此影片上傳元件應使用 `tus-js-client` 或 Uppy：

- 顯示真實位元組進度，不使用模擬百分比。
- 網路中斷時自動重試並從既有進度續傳。
- 顯示取消、重試與完成狀態。
- 上傳使用 Supabase direct storage hostname。
- 上傳成功後才建立 `site_media` 草稿資料。
- Database 寫入失敗時，立即嘗試刪除剛上傳的孤兒檔案。

官方參考：[Supabase Resumable Uploads](https://supabase.com/docs/guides/storage/uploads/resumable-uploads)

## 7. 權限與安全設計

### 7.1 後台登入

正式接上 Database 前，必須移除前端寫死的 `admin123`、`foodtruck2024` 及 `localStorage.admin_auth` 判斷，改成 Supabase Auth email/password。

建議流程：

1. 在 Supabase Auth 建立管理者帳號，不開放公開註冊。
2. 把允許管理內容的 `auth.users.id` 加入 `admin_users`。
3. 後台透過 `signInWithPassword` 登入。
4. 所有 Database 和 Storage 寫入由 RLS 再次驗證 `admin_users`。
5. 登出時呼叫 Supabase `signOut`，不只清除自訂 localStorage 值。

### 7.2 RLS 原則

- 未登入訪客：只能讀取 `published` 且在發布時間範圍內的媒體與有效連結。
- 已登入但不在 `admin_users`：不可新增、修改、刪除或上傳。
- 管理員：可讀取草稿、發布與封存內容，可管理 `site-media` bucket。
- `service_role` key 永遠不得出現在 HTML、JavaScript bundle、GitHub 或 Cloudflare Pages 前端環境變數。
- 公開網站內的 anon/publishable key 可以公開，但安全性必須由 RLS 保證。

### 7.3 RLS 判斷函式骨架

```sql
create or replace function public.is_site_admin()
returns boolean
language sql
stable
security definer
set search_path = public
as $$
  select exists (
    select 1
    from public.admin_users
    where user_id = auth.uid()
  );
$$;

revoke all on function public.is_site_admin() from public;
grant execute on function public.is_site_admin() to authenticated;

alter table public.site_media enable row level security;
alter table public.media_links enable row level security;
alter table public.media_change_log enable row level security;
```

`media_change_log` 建議只允許 trigger 寫入，不提供一般前端直接 INSERT policy；trigger function 必須固定 `search_path` 並只保存必要欄位。新增或移除 `admin_users` 也先由 Supabase Dashboard 或受保護的 owner-only server function 執行，不在一般編輯者後台開放。正式 SQL 應放入版本化 migration，不應只在 Dashboard 手動建立而沒有留檔。

## 8. 後台功能規格

### 8.1 導覽結構

沿用現有後台外框，但把媒體共用能力抽成一套：

```text
內容管理
  |- 跑馬燈
  |- 影片觀賞區
  `- 媒體庫
```

- 跑馬燈：只顯示 `placement = marquee`。
- 影片觀賞區：只顯示 `placement = video_gallery`。
- 媒體庫：可查全部素材、草稿、發布、封存及孤兒檔案。

### 8.2 影片新增流程

管理者點擊「新增影片」後選擇來源：

#### A. 上傳影片檔

1. 選取或拖曳 MP4。
2. 前端驗證 MIME、大小、長度、尺寸。
3. 顯示本機預覽。
4. 使用 TUS 上傳並顯示真實進度、速度與重試狀態。
5. 產生或上傳封面圖。
6. 在 `site_media` 建立 `draft`。
7. 填寫標題、說明、排序、上架區間。
8. 預覽桌面版與手機版。
9. 點擊「發布」後公開網站可讀取。

#### B. TikTok 連結

1. 貼上 TikTok 正式網址或 `vt.tiktok.com` 短網址。
2. 後台呼叫 `resolve-tiktok-url` Edge Function。
3. Function 只允許 TikTok 網域，限制重新導向次數與逾時。
4. 回傳 canonical URL、帳號與 video ID。
5. 建立 `provider = tiktok` 的草稿。
6. 預覽確認嵌入可載入後再發布。

若 Edge Function 尚未完成，第一版可以先要求輸入完整 `https://www.tiktok.com/@.../video/...` 網址，但短網址解析應列入第一階段，因為目前實際新增影片時會使用 TikTok 短網址。

### 8.3 跑馬燈新增流程

1. 選擇圖片或短影片。
2. 上傳素材並填寫標題、替代文字。
3. 新增零到多個按鈕連結，例如官網、LINE、FB、IG。
4. 選擇「永遠顯示」或「有排班時顯示」。
5. 若選擇排班條件，填入餐車正式名稱與別名。
6. 設定排序與發布時間。
7. 手機、平板、桌面預覽。
8. 發布。

### 8.4 列表管理

每張內容項目需要顯示：

- 縮圖或封面。
- 標題、來源、類型、檔案大小、影片長度。
- 草稿／已發布／已排程／已到期／已封存狀態。
- 排序控制；桌面可拖曳，手機提供上移、下移按鈕。
- 編輯、預覽、複製、封存操作。
- 最後更新時間與更新者。

排序應一次送出完整順序，由 Database RPC 在交易內更新，避免拖曳多筆時只成功一半。

### 8.5 刪除規則

- 一般「刪除」實際改成 `archived`，公開網站立即不再顯示。
- 硬刪除需要第二次確認，且先檢查檔案是否仍被其他內容引用。
- 硬刪除順序：封存資料、刪除 Storage 物件、刪除 Database 資料、寫入 change log。
- 若刪除 Storage 失敗，Database 保留記錄並標記待清理，不假裝全部成功。

## 9. 公開網站改造規格

### 9.1 資料讀取

新增共用的 `media-api.js`，集中處理：

- 建立或取得 Supabase client。
- 依 `placement` 讀取資料。
- 讀取 `media_links`。
- 解析 Storage 公開網址。
- 套用排班名稱比對。
- 錯誤、逾時與降級處理。

公開查詢只需要指定區域與排序；發布狀態和發布時間由 RLS 強制過濾，不能只依賴前端 `.eq('status', 'published')`。

### 9.2 影片區渲染

- `index.html` 只留下空容器，例如 `<div id="videoGallery" class="tiktok-grid"></div>`。
- 上傳影片使用 `<video controls playsinline preload="metadata">`。
- 手機版預設不自動播放，避免一次下載多支影片。
- TikTok 資料動態建立 blockquote，所有項目完成後只載入一次官方 `embed.js`。
- 資料載入完成後再呼叫目前的 `initializeTikTokCarousel()`，重建圓點及左右按鈕。
- 若影片為直式，容器固定 9:16；封面與載入狀態不得改變卡片尺寸。
- 影片無法播放時顯示封面、標題與「在新視窗開啟」連結，不留下空白區塊。

### 9.3 跑馬燈渲染

- 圖片使用 `<img loading="lazy">`。
- 短影片使用 `muted loop playsinline`，只在進入可視範圍時播放，離開可視範圍立即暫停。
- 使用者開啟「減少動態效果」時，不自動播放或自動滾動。
- 同一個媒體項目只建立一次；若內容寬度超過容器，再複製 DOM 供無縫循環。
- 更新週次後重新套用 `when_scheduled` 比對，但不重新下載已存在的檔案。
- 跑馬燈查詢失敗時先保留畫面穩定，不應清空已成功渲染的內容。

### 9.4 唯一公開入口

正式網站應指定 `index.html` 為唯一來源。`v2.html` 在功能確認後應改成導向 `index.html` 或移除，避免同一支影片在兩個檔案中出現不同版本。

## 10. 快取與版本策略

### 10.1 Database 資料

- 媒體清單每次完整載入頁面時向 Supabase 查詢。
- 第一階段不要再把媒體清單永久放在 `localStorage`。
- 可使用記憶體或 `sessionStorage` 做最多 5 分鐘的短快取，但必須保存 `fetchedAt`。
- 頁面從背景回到前景時，若資料超過 5 分鐘就重新讀取。
- `pageshow` 的 `persisted = true` 時重新讀取，以處理 Safari/LINE 內嵌瀏覽器的返回快取。
- 後台發布成功後立即重新查詢正式資料，不能只相信本地 React state。

Supabase Realtime 可以在第二階段加入，讓已開啟的網站即時收到更新；目前內容更新頻率不高，先使用「載入與回到前景時重抓」較簡單，也更容易除錯。

### 10.2 Storage 檔案

- 每一版檔案都使用新 URL，不覆蓋原路徑。
- 上傳時可設定長效 `cacheControl`，例如一年。
- Database 指向新路徑後，使用者會自然取得新檔。
- 舊檔保留短暫回復期，再由清理流程刪除。

Supabase 官方也建議避免覆寫同一路徑，因為 CDN 節點需要時間傳播變更。官方參考：[Storage CDN](https://supabase.com/docs/guides/storage/cdn/fundamentals)、[Serving Storage Assets](https://supabase.com/docs/guides/storage/serving/downloads)

### 10.3 Cloudflare Pages 靜態檔

目前 `_headers` 對全部檔案設定 `no-store`。短期可繼續使用以確保 HTML、固定檔名 JavaScript 與 CSS 不殘留舊版；中期建議把公開網站也納入 Vite build：

- HTML：`no-cache, must-revalidate`。
- 有內容雜湊的 JS/CSS：`public, max-age=31536000, immutable`。
- 不再靠手動修改 `?v=v2.0.1` 維護版本。
- Supabase Storage 素材由 Storage 自己的 CDN 與 `cacheControl` 管理，不受 Pages `_headers` 影響。

### 11.1 遷移對照

### 11.2 遷移順序

1. 匯出 Supabase Database 備份、現有 `data.json`、TikTok 清單及外部媒體 URL 清單。
2. 建立新資料表、RLS、Storage bucket 與測試管理員。
3. 先匯入內容為 `draft`，不得直接發布。
4. 後台逐筆預覽圖片、影片、TikTok 與連結。
5. 新前端以 feature flag 讀取 Supabase，但保留舊版降級資料。
6. 在測試網址確認後切換正式來源。
7. 觀察至少一個發布週期，再移除硬編碼 TikTok、`data.json` 主來源及 localStorage 媒體快取。
8. 最後停用不再使用的 Cloudinary unsigned upload 與 Apps Script 入口。

### 11.3 回復方式

- 發布切換前保留舊版 Git commit 和資料匯出。
- 前端保留 `MEDIA_SOURCE = 'legacy' | 'supabase'` 的短期切換設定。
- 新資料讀取失敗時可暫時切回 legacy，不回滾行程表 Supabase 整合。
- 所有搬移檔案建立 manifest，記錄舊 URL、新 bucket/path、資料列 ID、檔案大小與雜湊。

## 13. 測試與驗收

### 13.1 Database 與權限

- anon 可讀已發布、有效時間內資料。
- anon 不可讀草稿、封存、未開始或已到期資料。
- anon 不可 INSERT、UPDATE、DELETE。
- 一般 authenticated 使用者不在 `admin_users` 時不可寫入。
- 管理員可完成 CRUD 與 Storage 上傳。
- service role 不存在於前端 bundle。

### 13.2 上傳與資料一致性

- 5 MB、20 MB、100 MB MP4 上傳測試。
- 模擬網路中斷後可續傳。
- 不合法 MIME、超過大小、超過長度會在上傳前阻擋。
- Storage 成功但 Database 失敗時不留下永久孤兒檔。
- 同名檔案重傳會產生新 URL。
- 封存內容立即從公開查詢消失。
- 排程開始、結束時間跨台北時區仍正確。

### 13.3 公開網站

- 桌面寬度下影片排列正確。
- 手機只顯示一支主要影片，不裁切 TikTok 內容。
- 手機可左右滑動，也可使用左右按鈕和圓點。
- iOS Safari 原生影片可 `playsinline`，不會被迫全螢幕。
- Android Chrome、Safari、Chrome 桌面版可播放。
- TikTok script 只載入一次。
- 資料空白、API 逾時、單支影片失效時不影響其他區塊。
- 跑馬燈圖片與短影片不造成版面跳動。
- `prefers-reduced-motion` 時停止非必要自動動畫。

### 13.4 快取情境

- 管理員發布新內容後，無痕視窗可立即讀到。
- 已開啟分頁放置超過 5 分鐘後回到前景會更新。

## 16. 何時升級到 Cloudflare Stream

第一階段不必立即增加 Stream 成本。以下任一情況持續發生時再升級：

- 行動網路播放常出現緩衝或檔案下載過大。
- 需要依使用者網速自動切換 360p、720p、1080p。
- 需要影片轉碼、HLS/DASH、觀看分析或 signed playback。
- 直接上傳影片數量與觀看量大幅成長。
- 不希望管理者在上傳前自行壓縮成網站相容格式。

Cloudflare Stream 會自動編碼並以 adaptive bitrate 提供影片，適合後續規模化；Storage 和 Database 的責任仍應分開。官方參考：[Cloudflare Stream](https://developers.cloudflare.com/stream/)、[Upload Videos](https://developers.cloudflare.com/stream/uploading-videos/)、[Stream Pricing](https://developers.cloudflare.com/stream/pricing/)

1. 先完成 Supabase Auth、RLS、Database schema、Storage policy。
2. 再把現有後台的影片管理接成真實 CRUD 與上傳。

## 20. 跨年度日期與排序修正（優先項目）

補充日期：2026-10-03。此節列為 P0 必要工作，應在啟用跑馬燈排班條件前完成。

### 20.1 現有問題與影響

| 現有行為 | 程式位置 | 影響 |
|---|---|---|
| 解析日期只取月份、日期 | `sheets-booking.js` 的 `parseBookingDate()` | 無法辨認不同年度的同一天 |
| 日期分組 key 使用 `month-day` | `convertBookingDataToSchedule()` | 2026/1/5 與 2027/1/5 可能被合併 |
| 先按月份、日期排序 | `convertBookingDataToSchedule()` | 跨年同一週內，一月可能排在十二月前面；後續週排序不能修正週內順序 |
| 一月用 timestamp 推估年份 | `convertBookingDataToSchedule()` | 十二月建立的隔年一月預約可能在一月被誤藏 |
| 依目前月份猜測去年或明年 | `getMondayKey()` | 同一筆資料隨查看時間而改變年度，歷史與較遠未來行程無法可靠排序 |
| 跑馬燈只在十一、十二月將一月當作隔年 | `sheets-marquee.js` | 日期規則與行程表不同，過期判斷與餐車顯示可能不一致 |

上述是依程式確認的設計缺陷；本文件尚未修改正式日期程式或資料庫。

### 20.2 統一日期規格

- 在 `foodcarcalss` 新增 `service_date date`，完整保存 `YYYY-MM-DD` 營業日期。
- `booking_date` 舊文字欄位暫時保留，供現有流程相容與遷移比對。
- `created_at`、`timestamp` 只代表建立資料的時間，不得作為營業年份。
- 查詢以 `service_date` 排序，分組使用完整 ISO 日期。
- 週分組用該日期所在週的週一完整日期作 key，例如 `2026-12-28`。
- 每週內的日期再按 `service_date` 遞增排序。
- 跨年週標題顯示年份，例如 `2026/12/28 - 2027/1/3`；週 ID 使用穩定日期，不用陣列索引。
- 跑馬燈排班條件與過期判斷共用 `service_date`，不再從 DOM 月日猜測年份。
- 營業日期屬於台北日曆日期，避免將 `new Date('YYYY-MM-DD')` 的 UTC 解析結果直接拿來做本地日曆運算。
- 媒體發布的 `publish_start/end` 維持 `timestamptz`；後台輸入及顯示使用 `Asia/Taipei`，資料庫保存絕對時間。
- 媒體手動 `sort_order` 與行程日期排序分開；不以 UUID、月份文字或媒體建立年份代替營業日期。

### 20.3 遷移與相容策略

1. 先新增可為空的 `service_date`，不破壞目前資料寫入流程。
2. 有完整年月日的原始資料可直接轉換，並檢查日期合法性。
3. 只有月日的舊資料，優先從原始排班年度、活動期間或來源工作表取得年份。
4. 無法確認年度的資料列入人工確認清單；不得一律套用當前年份或建立年份。
5. 更新所有新增、修改、匯入行程入口，使其寫入完整日期。
6. 新前端優先讀取 `service_date`；缺少日期的舊資料須走明確的相容規則並留下提示，不混入已確認日期的正式排序。
7. 完成逐筆確認與新舊結果比對後，再要求新資料的 `service_date` 必填。
8. 刪除月日推算年度及 timestamp 判斷營業年度的舊邏輯。
